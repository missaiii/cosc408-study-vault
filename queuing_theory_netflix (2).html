Queue Disciplines

  • FIFO / FCFS — First Come, First Served. Most common. Customers served in order of arrival.
  • LIFO / LCFS — Last Come, First Served. Most recent arrivals served first (e.g. stack-based processing).
  • SIRO — Service In Random Order. Next customer chosen randomly from waiting pool.
  • Priority — Each arrival classified into priority categories. Within each level, FCFS applies.
⚠️ Balking = customer arrives but refuses to join. Reneging = customer joins then leaves. Jockeying = switching between queues.
🖥️

Server Arrangements

  • Servers in Parallel — All servers provide the same service type. Customer needs only ONE server to complete service. E.g. bank tellers, supermarket checkouts.
  • Servers in Series — Customer must pass through MULTIPLE servers sequentially before service is complete. E.g. hospital admission → triage → doctor → pharmacy.

One queue, one server. Simplest model. E.g. a single ATM machine. Described as M/M/1 in Kendall-Lee notation.

Two parallel servers, each providing identical service. Customers join a single shared queue or separate queues. E.g. two checkout lanes.

Two identical service channels, each with 3 distinct service points (A→B→C). Jockeying may be permitted between lines.

Three identical service channels, each with 2 distinct service points (A→B). Used when there is high parallel demand and a two-step process.

M=c, PHASE=k

General Multi-Channel/Phase

The general form with c parallel channels and k phases per channel. Most real hospital and manufacturing systems fall here.

FINITE K

Finite Capacity System

Queue has a maximum size K. Customers arriving when the system is full are turned away (lost). Used for call centres, parking lots.

Arrival Patterns

Random (Poisson) Arrivals

The most common assumption. Arrivals occur independently and randomly. The number of arrivals in any fixed interval follows a Poisson distribution with parameter λ.

P(k arrivals) = (λᵏ · e⁻λ) / k!

Time-Dependent Arrivals

λ varies across the day (e.g. lunch rush, morning commute). Requires time-segmented modelling or simulation rather than a single steady-state formula.

Assumptions to State Explicitly

  • Steady-state operation (system in equilibrium)
  • Independent, identically distributed (IID) service times
  • No bulk arrivals (one customer at a time)
  • No balking, reneging, or jockeying (unless specified)
  • Infinite calling population (unless finite source model)
  • FCFS queue discipline (unless stated otherwise)

Identifying Bottlenecks & Limitations

🔴

Bottleneck Detection

A bottleneck is any stage where ρ approaches 1. When utilisation nears 100%, queue length grows exponentially and the system becomes unstable. Monitor Lq and Wq to identify the chokepoint.

📊

Theoretical vs Observed

Theoretical Distribution: derived from average arrival rate λ using Poisson formula.

Observed Distribution: constructed from actual system observations. May or may not be Poisson — always verify with goodness-of-fit tests (χ² test).

⚡

Critical Constraint

For the system to be stable and have a finite-length queue:

μ > λ

If λ ≥ μ, the queue grows to infinity — there is NO steady-state solution.

M/M/1 Model (1 server)

Single-channel, Poisson arrivals, exponential service times, infinite queue capacity. The foundational queuing model.

ρ = λ / μ   (utilisation)
P₀ = 1 − ρ   (idle probability)
L = λ / (μ − λ)
Lq = λ² / [μ(μ − λ)]
W = 1 / (μ − λ)
Wq = λ / [μ(μ − λ)]

M/M/c Model (c servers)

Multi-channel, Poisson arrivals, exponential service, one shared queue. Effective service rate = c·μ. Requires ρ = λ/(c·μ) < 1.

ρ = λ / (c·μ)   (utilisation)
Mμ = c × μ   (effective service rate)
P₀ = computed via Erlang-C formula
Lq = P₀·(λ/μ)^c·ρ / [c!·(1−ρ)²]
L = Lq + λ/μ
Wq = Lq / λ

Little's Law — The Universal Connector

System
L = λ · W
Queue only
Lq = λ · Wq
Time relationship
W = Wq + 1/μ

Little's Law holds for ANY queuing system regardless of the distribution — Poisson, deterministic, or general. It is a model-independent identity.

Module D — Stochastic Processes

System Uncertainty & Randomness

Understand Poisson processes, Markov chains, IID assumptions, and exponential distributions — and when each is valid in practice.

📡 Poisson Process

Models random arrivals. The Poisson distribution gives the probability of k arrivals in a fixed interval given average rate λ. Key properties:

  • Arrivals are independent of each other
  • Average rate λ is constant over time
  • At most one arrival per instant
  • Inter-arrival times follow Exponential(λ)
Valid when: customer arrivals are truly random with no clustering. E.g. website hits, student inflow to a library, patient arrivals to a walk-in clinic.
Poisson distribution (λ=3)

🔄 Markov Process

Models system state transitions. A process is Markovian (memoryless) when the probability of transitioning to the next state depends ONLY on the current state — not on history.

  • State space = {0, 1, 2, 3, ...} customers in system
  • Transition rates: λ (arrival) and μ (service departure)
  • Birth-death process: arrivals "birth" the queue, departures "kill" it
The memoryless property of the exponential distribution is what makes M/M/1 tractable — remaining service time doesn't depend on time already spent.

⚖️ IID Assumption

Independent and Identically Distributed — the assumption that all service times (and inter-arrival times) are drawn from the same distribution independently.

  • Identical: same distribution, same parameters for every customer
  • Independent: one customer's service time has no effect on the next

This assumption simplifies analysis enormously. In practice it may be violated when:

  • Server fatigue changes μ over time
  • Customer complexity varies systematically (priority classes)
  • Time-of-day effects alter both λ and μ
Always state and justify the IID assumption. If it fails, Monte Carlo simulation (Module E) is the appropriate tool.

📉 Exponential Distribution

The continuous probability distribution most commonly used for both inter-arrival times and service times in queuing theory. Parameter = rate.

f(t) = μ·e−μt   (PDF)
E[T] = 1/μ   (mean service time)
P(T > t) = e−μt   (survival)
  • Memoryless: P(T>s+t | T>s) = P(T>t)
  • Only continuous memoryless distribution
  • High variance: Coefficient of Variation = 1
When exponential service is NOT realistic (e.g. fixed-time operations like manufacturing), use M/D/1 (deterministic service) or G/G/1 (general service) models.

System Behaviour Analysis

Utilisation (ρ)

ρ = λ / (c·μ)
  • ρ < 1: stable system, finite queue
  • ρ → 1: queue grows rapidly to very large values
  • ρ ≥ 1: unstable, queue grows to infinity
  • ρ = 0.5: server busy 50% of the time

Queue & Wait Interpretation

  • Low Lq, low Wq: efficient system, little waiting
  • High Lq, high Wq: bottleneck — add servers or increase μ
  • Lq grows NON-linearly as ρ → 1 (exponential blowup)
  • Doubling μ does NOT halve W — effect is non-linear

Operational Performance

  • Throughput: rate at which customers complete service = λ (at steady state)
  • Efficiency: high ρ = servers kept busy, but customer experience suffers
  • Trade-off: adding capacity (↑c or ↑μ) reduces Wq but increases cost
  • Optimal design: minimise total cost = waiting cost + service cost
Module E — Monte Carlo & Decision Modelling

Simulation Under Uncertainty

Define uncertain variables, assign distributions, run repeated sampling, and interpret outcomes for real decisions. Monte Carlo is the tool when analytical formulas don't apply.

The Monte Carlo Pipeline

List every variable that is uncertain or random: arrival rate λ, service time, demand, prices, costs. Distinguish uncertain variables from known constants. For each uncertain variable, define its possible range and shape of uncertainty.
Choose a distribution that matches what you know. Triangular(min, mode, max) is ideal when you have expert estimates but no historical data. Poisson for random counts. Exponential for service times. Normal for sums of many effects. Uniform when all values are equally likely in a range.
For each trial: sample a value for every uncertain variable from its distribution, compute the outcome (profit, queue length, service time). Repeat N times (typically 1,000–100,000). Each trial is independent.
Compute expected value (mean of all trials), variance/std dev (spread of outcomes), percentile ranges (e.g. 90% chance of outcome < X), and probability of loss or failure. Use these to make risk-informed decisions rather than relying on a single-point estimate.
As N → ∞, the simulated mean converges to the true expected value. More trials = more reliable estimates. But convergence is slow for rare events in the tails. 10,000 trials is usually sufficient for typical business decisions.

Module F — Data Modelling

Forecasting & Integration

Combine historical data and real-time signals to build forecasting logic. Understand data requirements, model assumptions, and validation techniques.

📂 Data Requirements

  • Historical arrival timestamps to estimate λ
  • Service completion times to estimate μ
  • Queue length observations at regular intervals
  • System capacity information (K)
  • Enough data to test for Poisson / exponential fit

Minimum: 30–50 independent observations per parameter to be estimated.

🔑 Key Drivers

  • Time of day / day of week effects on λ
  • Seasonal demand patterns
  • Server skill heterogeneity (affects μ)
  • Equipment reliability (affects μ variability)
  • Customer mix / complexity (affects service time)

Use regression or time-series decomposition to extract these drivers from data.

✅ Validation Techniques

  • χ² goodness-of-fit: test if observed arrivals match Poisson distribution
  • K-S test: compare service times to exponential CDF
  • Residual analysis: check model predictions vs actual queue lengths
  • Cross-validation: train on past data, validate on held-out period
  • Sensitivity analysis: vary λ ± 20% — how much does Lq change?

🔮 Forecasting Logic

  • Moving average for short-term λ estimation
  • Exponential smoothing to weight recent data more
  • Time-series models (ARIMA) for seasonal patterns
  • Real-time sensor data to update model parameters continuously
Forecasted λ feeds into queuing formulas → predicted Lq, Wq → staffing decisions for the next period.

⚠️ Model Assumptions & Limitations

  • Steady-state formulas assume time-averaged equilibrium
  • Poisson assumption may fail during rush hours
  • Historical data may not reflect future structural changes
  • Simulation can accommodate non-stationary arrivals; formulas cannot
  • All models are wrong — some are useful

🔗 System Integration

  • Combine queuing model output with financial model (cost/hr of waiting)
  • Feed Wq prediction into customer satisfaction scoring
  • Use Lq forecast to trigger automatic server allocation
  • Validate simulation output against real observed L and W
End-to-end thinking: data → model → decision → action → feedback → data.
Module G — Exam Mastery

Demonstrate Mastery

Structured guidance to score full marks across all five modelling dimensions. The examiner wants to see end-to-end system thinking, not just formulas.

01

Always start with the conceptual model

Before writing any formula, identify: what are the entities (customers)? What is the server? What is the queue discipline? Draw the flow diagram: Arrival → Queue → Service → Exit. Label each arrow with the relevant variable (λ, μ). Examiners award marks for structured setup.

02

Write out Kendall-Lee notation explicitly

State the full A/S/c/K/N/D notation for every model you analyse. If K=∞ and N=∞, still write it out. Then justify each choice: "Arrivals are Poisson (M) because they are random and independent. Service is exponential (M) because of the memoryless property..."

03

Check stability FIRST before computing anything

Always compute ρ = λ/(c·μ) before applying any formula. If ρ ≥ 1, state: "The system is UNSTABLE. The queue grows without bound. The M/M/c formulas do not apply. We need to increase c or μ, or reduce λ."

04

State ALL assumptions explicitly

IID service times, Poisson arrivals, FCFS discipline, infinite population, steady-state operation. If any assumption is questionable for the given scenario, say so. Noting limitations shows higher-order thinking and earns interpretation marks.

05

Interpret numbers in operational terms

Don't just write "Lq = 3.6". Write: "On average, 3.6 customers are waiting in the queue. At £15/hour opportunity cost, this represents £54/hour of lost value. Adding a second server reduces Lq to 0.5, saving £46/hour — easily justifying the server cost."

06

Link stochastic concepts to the model

For every model, explain WHY Poisson and exponential are appropriate: "The memoryless property of the exponential distribution ensures Markovian transitions, making the M/M/1 model analytically tractable." This demonstrates understanding beyond formula substitution.

07

Use Little's Law as a cross-check

After computing L, Lq, W, Wq — verify: Does L = λ·W? Does Lq = λ·Wq? Does W = Wq + 1/μ? If not, you have made an arithmetic error. Little's Law is a model-free identity that always holds.

08

Monte Carlo: focus on decision, not just simulation

In Monte Carlo questions, always end with: "Based on N trials, the expected outcome is X with a standard deviation of Y. There is a Z% probability of loss/failure. Therefore the recommended decision is..." — the simulation is a means to a decision, not the end goal.
